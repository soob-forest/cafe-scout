- [x] 시간대 경계, 빈 구간, 자정 전후, 다중 관찰 평균, 사용자 격리를 테스트한다.

## 16. 구현 적합성 재검토 보완

아래 순서는 데이터 정합성 회귀 테스트 → DB 경계 강화 → UI 복구 → 운영 안전성 → 전체 재검증 순이다. 16.1과 16.2는 P0 출시 차단 항목이다.

### 16.1 사진 부분 실패와 정렬 정합성 — P0 출시 차단

- [x] 복수 사진에서 `앞 사진 성공 + 뒤 사진 실패`, `앞 사진 실패 + 뒤 사진 성공`, 여러 종류가 섞인 부분 실패를 재현하는 컴포넌트/E2E 회귀 테스트를 먼저 추가한다.
- [x] 파일을 선택하거나 업로드 배치를 시작할 때 종류별 안정적인 `sortOrder`를 부여하고 재시도에서도 같은 순서를 유지한다.
- [x] metadata 확정 성공 응답에 저장된 사진 정보를 반환하고, 성공 사진을 `storedPhotos`에 병합하거나 서버에서 다시 조회하여 클라이언트 상태를 DB와 동기화한다.
- [x] 재시도는 실패한 사진만 대상으로 하며 이미 성공한 사진의 object/metadata를 중복 생성하지 않는다.
- [x] 사진 순서 변경을 전체 종류별 ID 집합을 검증하는 단일 transaction/RPC로 처리하고 일부 update만 반영되는 상태를 막는다.
- [x] `(cafe_visit_id, kind, sort_order)` 중복을 DB에서 거부하되 순서 교환이 가능한 deferrable unique 제약 또는 동등한 원자적 재정렬 방식을 적용한다.

완료 기준: 부분 실패를 몇 번 재시도해도 화면과 DB의 사진 수·종류·순서가 일치하고 GENERAL 대표 사진 선택이 결정적이어야 한다.

### 16.2 사진 보안·개수 제한의 DB 경계 강화 — P0 출시 차단

- [x] 동시 finalize 두 건이 종류별 10장/3장 경계를 넘지 못하는 통합 테스트를 추가한다.
- [x] 사진 metadata 확정을 방문 행 잠금과 함께 수행하는 transaction/RPC로 옮겨 object 존재, 소유자/방문 경로, MIME, 크기, 종류별 개수와 정렬 순서를 한 경계에서 검증한다.
- [x] `object_path`가 `{owner_id}/{cafe_visit_id}/...` 형식인지 DB 제약 또는 확정 함수에서 검증한다.
- [x] 인증 사용자의 `cafe_photos` 직접 insert/update/delete 권한을 제거하고 검증된 확정·제거·재정렬 함수만 허용한다. 조회 권한과 사용자별 RLS는 유지한다.
- [x] 존재하지 않는 Storage object, 위조 MIME/크기, 잘못된 방문 경로, 직접 metadata insert가 모두 거부되는 통합 테스트를 추가한다.
- [x] 제한 초과나 metadata 확정 실패 시 이번 시도의 Storage object가 제거되고 고아 점검 대상도 정확히 유지되는지 검증한다.

완료 기준: UI, 다중 탭, REST/RPC 직접 호출 여부와 관계없이 사진 제한과 metadata 무결성이 동일하게 강제되어야 한다.

### 16.3 날짜 입력과 필드 오류 접근성

- [x] `datetime-local` 변환 유틸리티가 빈 문자열과 잘못된 날짜를 예외 없이 처리하도록 하고 방문 일시와 추가 관찰 시각에 같은 검증 경계를 적용한다.
- [x] 방문 일시를 비운 직후와 추가 관찰 시각을 비운 채 저장하는 컴포넌트/E2E 회귀 테스트를 추가한다.
- [x] 모든 Zod 오류 path를 안정적인 input ID와 연결하고 각 필드에 `aria-invalid`, `aria-describedby`, 인라인 한국어 오류를 제공한다.
- [x] 상단 오류 요약의 각 항목을 해당 필드 링크로 만들고 저장 실패 후 첫 오류 필드 또는 오류 요약으로 포커스를 이동한다.
- [x] 숫자 범위, 영업시간, 메뉴 항목, 점유 입력 모드와 날짜 오류를 키보드 및 스크린리더 기준으로 다시 검증한다.

완료 기준: 잘못된 입력이 예외나 페이지 오류를 만들지 않고, 사용자가 오류 요약과 해당 필드를 양방향으로 식별할 수 있어야 한다.

### 16.4 매출 추정 모델 단일화와 parity 검증

- [x] 저장 RPC와 snapshot trigger에 중복된 계산을 하나의 DB 계산 함수로 통합하고 Server Action의 사용되지 않는 `estimateBusiness` 호출을 제거한다.
- [x] 시나리오 계수, 체류시간, 테이크아웃 계수, 신뢰도 점수와 모델 버전을 버전화된 모델 계약으로 관리하고 TS 미리보기와 DB 계산이 같은 계약을 참조하도록 한다.
- [x] PRD 기준값뿐 아니라 0, 경계값, 자정 넘김, 초과 고객, 테이크아웃 전 구간, 계산 불가 조합을 TS와 실제 DB에 동시에 입력하는 parity integration test를 추가한다.
- [x] 모델 계약이 달라지면 테스트가 실패하고, 의도적 변경에는 새 `estimationModelVersion`과 migration이 필요하도록 문서화한다.

완료 기준: 저장 경로 안의 계산 구현은 한 곳뿐이고, 브라우저 미리보기와 DB snapshot의 모든 공개 결과가 golden fixture에서 일치해야 한다.

### 16.5 백업·복구 대상 프로젝트 안전장치

- [x] Hosted 백업에 `SUPABASE_PROJECT_REF`, 복구에 `TARGET_SUPABASE_PROJECT_REF`를 필수로 받고 현재 CLI link와 일치하지 않으면 실행 전에 중단한다.
- [x] DB URL이 가리키는 project ref와 명시한 Storage project ref를 가능한 범위에서 교차 확인하고, 확인할 수 없으면 사용자가 정확한 ref를 다시 입력해야 진행되게 한다.
- [x] 복구는 `CONFIRM_RESTORE_PROJECT_REF=<target-ref>`처럼 대상 ref 자체를 확인값으로 요구하고 실행 전 DB/Storage 대상을 함께 출력한다.
- [x] 기존 파일이 섞이지 않도록 백업 대상 디렉터리가 비어 있지 않으면 중단하거나 명시적 새 디렉터리를 요구한다.
- [x] 서로 다른 DB/Storage ref, 누락된 ref, 비어 있지 않은 백업 디렉터리에서 스크립트가 실제 변경 전에 실패하는 자동 테스트를 추가한다.
- [x] 안전장치를 `RECOVERY.md`에 반영하고 로컬 복구 훈련을 다시 실행한다.

완료 기준: DB와 Storage를 서로 다른 프로젝트에서 백업하거나 서로 다른 프로젝트로 복구하는 명령이 실제 작업 전에 반드시 실패해야 한다.
