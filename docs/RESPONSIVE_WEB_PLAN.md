# 모바일·태블릿 반응형 웹 개선 계획

- 작성일: 2026-08-30
- 상태: 구현 전 계획
- 대상: 공개 홈·로그인·앱 셸·방문 목록·방문 입력/수정·상세·비교 화면

## 1. Problem 1-Pager

### 배경

Cafe Scout는 현장에서 3~5분 안에 방문 정보를 입력하고 결과를 확인하는 도구다. 현재도
`820px`, `480px` 기준의 반응형 규칙과 desktop/tablet/mobile E2E 프로젝트가 있지만,
태블릿 세로 화면과 작은 모바일에서 핵심 조작을 안정적으로 보장하는 수준의 기준선과 회귀
검사가 부족하다.

### 문제

- 반응형 규칙이 `src/app/globals.css` 한 파일 2,113줄에 섞여 있어 변경 영향도를 격리하기 어렵다.
- 입력 화면은 `820px` 이하에서 예상 매출 패널이 본문 아래로 이동한다. 태블릿 세로 화면에서
  입력과 추정치를 함께 본다는 제품 명세와 맞지 않는다.
- 아이콘·칩·별점·사진 정렬 등 일부 조작 영역이 44px보다 작아 터치 오조작 가능성이 있다.
- 하단 내비게이션과 비교 바는 고정 배치지만 safe area와 모바일 키보드, 두 고정 요소의 겹침을
  검증하는 기준이 없다.
- 비교표만 의도적으로 가로 스크롤을 허용하지만, 그 사실을 시각적으로 알려 주거나 첫 열을
  유지하는 보조 장치가 부족하다.
- E2E는 Pixel 7과 1024px 태블릿만 다룬다. 360px 모바일, 768px 태블릿 세로, 화면 회전,
  긴 문자열, 최대 입력, 의도하지 않은 가로 overflow를 검사하지 않는다.

### 목표

- 320~1,440px에서 비교표·사진 스트립을 제외한 페이지 가로 overflow를 제거한다.
- 모바일과 태블릿에서 로그인 → 목록 → 입력/저장 → 상세 → 비교의 핵심 작업을 가림이나 겹침
  없이 완료할 수 있게 한다.
- 태블릿 세로/가로 화면에서는 입력 본문과 실시간 예상 매출을 함께 볼 수 있게 한다.
- 주요 터치 조작 영역을 최소 44×44px로 만들고 키보드 초점·오류 이동·200% 확대를 보장한다.
- 기존 데스크톱 시각 언어와 도메인·저장 동작을 유지하며 뷰포트 회귀 검사를 자동화한다.

### 비목표

- 브랜드 재디자인, 계산 모델, 데이터 구조, 인증·사진 저장 정책 변경
- 네이티브 앱 또는 PWA 전환
- Tailwind 등 새 스타일 프레임워크 도입
- 이번 작업과 무관한 기능 추가

### 제약 및 가정

- Next.js 16.3.1의 저장소 내 가이드를 기준으로 작업한다. 전역 CSS는 하나의 진입점에서 예측
  가능한 순서로 불러오고, 기본 viewport 동작을 불필요하게 덮어쓰지 않는다.
- 우선 지원 환경은 최근 iOS/iPadOS Safari와 Android Chrome이며 기준 폭은 360, 390/412,
  768, 1,024, 1,440px이다. 320px은 최소 폭 회귀 검사에 포함한다.
- 기존 하단 내비게이션은 유지하되, 기준선 테스트에서 정보 구조 문제가 확인되면 별도 결정으로
  분리한다.
- 비교표와 사진 스트립은 의도된 내부 가로 스크롤을 유지한다. 그 외 가로 스크롤은 결함이다.
- 실제 브라우저 기준선 캡처는 구현 시작 전에 수행한다. 계획 작성 시에는 연결 가능한 브라우저
  인스턴스가 없어 코드와 기존 테스트를 기준으로 현황을 판단했다.
- 위 가정과 지원 범위는 구현 Issue/PR 본문에도 기록한다.

## 2. 현재 구현과 영향 범위

| 영역        | 현재 상태                                     | 주요 파일                                              |

| 앱 셸       | 데스크톱 상단 메뉴, 820px 이하 하단 고정 메뉴 | `src/components/app-shell.tsx`                         |

화면별 규칙을 분리한 뒤 작업한다.

## 3. 접근 대안 비교

| 대안                                     | 장점                                     | 단점                                          | 주요 위험                                      |
| ---------------------------------------- | ---------------------------------------- | --------------------------------------------- | ---------------------------------------------- |
| A. 기존 `globals.css`에 media query 추가 | 가장 빠르고 마크업 변경이 적다           | 2,113줄 전역 결합과 중복을 더 키운다          | 한 화면 수정이 다른 화면을 깨뜨릴 가능성       |
| B. Tailwind/CSS Modules로 전면 재작성    | 장기적인 스타일 격리가 쉽다              | 모든 class와 화면을 동시에 바꾸는 큰 작업이다 | 기능 회귀, 일정 확대, 시각 차이 누적           |
| C. 기존 class를 유지한 점진적 분리·개선  | 작은 PR, 쉬운 rollback, 기존 디자인 보존 | 먼저 무동작 스타일 분리가 필요하다            | CSS import 순서 차이; build와 화면 diff로 완화 |

**선택: C.** 하나의 CSS 진입점은 유지하되 토큰·기반·셸·목록·폼·상세·비교·반응형 규칙을
각 300줄 이하 파일로 분리한다. 이후 공통 기반부터 화면 단위로 개선한다. 새 프레임워크는 도입하지
않는다.

## 4. 작업 단계

### 0단계 — 기준선과 결정 기록

- 구현 Issue에 지원 브라우저, 기준 뷰포트, 허용 overflow, 비목표와 가정을 기록한다.
- seed 데이터로 홈, 로그인, 목록, 빈 목록, 입력 기본/오류/최대 항목, 상세, 비교 2개/3개 화면을
  각 기준 폭에서 캡처한다.
- 각 화면의 `scrollWidth`, 고정 요소 겹침, 긴 카페명·지역·금액, 세로/가로 회전을 점검하고 결함
  목록에 우선순위를 붙인다.
- 완료 기준: 변경 전 캡처와 결함 목록이 Issue에 있고, P0 핵심 흐름의 기준선이 재현 가능하다.

### 1단계 — 동작을 바꾸지 않는 구조 정리

- `globals.css`를 단일 진입점으로 남기고 토큰/기반, 공개 화면, 앱 셸, 목록, 폼, 상세, 비교 파일을
  명시적 순서로 import한다. 모든 스타일 파일은 300줄 이하로 유지한다.
- 1,460줄 `VisitForm`은 상태·저장 orchestration과 화면 section을 분리한다. 공개 API와 DOM 순서,
  필드 id, aria 연결은 유지하고 기존 컴포넌트 테스트로 동등성을 확인한다.
- 반응형 마크업 수정이 필요한 상세 화면도 300줄 제한을 넘지 않도록 지표·메뉴·고객·사진 section을
  작은 컴포넌트로 분리한다.
- 완료 기준: 의도된 시각 변화가 없고 format/typecheck/lint/unit/component/build/E2E가 통과한다.

### 2단계 — 공통 반응형 기반과 앱 셸

- 콘텐츠 기준으로 mobile `≤767px`, tablet `768~1023px`, desktop `≥1024px` 구간을 정리하고
  경계값 앞뒤에서도 연속적으로 resize해 확인한다.
- 간격·글자·컨테이너 폭을 `clamp()` 기반 토큰으로 정리하고 모든 grid/flex 자식에 필요한
  `min-width: 0`, 긴 문자열 줄바꿈, 이미지 최대 폭을 적용한다.
- `100dvh`, `env(safe-area-inset-*)`, 하단 내비게이션 높이 토큰을 적용해 홈·로그인·앱 본문과
  고정 요소의 여백을 일관되게 만든다.
- 주요 링크·버튼·칩·아이콘 조작 영역을 44×44px 이상으로 맞추고 hover 전용 피드백에는 focus와
  active 상태를 함께 제공한다. `prefers-reduced-motion`도 처리한다.
- 완료 기준: 셸 자체의 가로 overflow가 없고 하단 메뉴가 콘텐츠·비교 바·safe area와 겹치지 않는다.

### 3단계 — 공개 화면과 방문 목록

- 홈의 2열 preview를 태블릿/모바일에서 자연스럽게 1열로 바꾸고 `100vh` 의존을 제거한다.
- 로그인 2열 → 1열 전환을 실제 콘텐츠 폭 기준으로 앞당기고 작은 화면에서 카드가 viewport 밖으로
  나가지 않게 한다.
- 목록은 desktop 3열, tablet 2열, mobile 1열을 유지하되 이미지 비율과 카드 높이를 안정화한다.
- 선택 버튼과 고정 비교 바를 터치 크기·safe area에 맞추고 최대 선택/비활성 상태를 읽기 쉽게 한다.
- 완료 기준: 긴 이름·지역과 사진 없음 상태에서도 카드/버튼이 잘리지 않고 비교 진입이 가능하다.

### 4단계 — 방문 입력/수정

- tablet에서는 유동 폭 본문 + 280~340px sticky 예상 패널을 유지한다. mobile에서만 단일 열로
  전환하고 각 2/3열 필드는 가용 폭에 따라 1열 또는 2열로 재배치한다.
- mobile에는 전체 예상 카드와 별도로 현재 기준 매출 + 저장 상태를 보여 주는 compact sticky action을
  하단 메뉴 위에 둔다. 키보드가 열리거나 오류로 이동할 때 입력을 가리지 않도록 한다.
- 메뉴 행을 mobile 카드형 grid로 바꾸고 메뉴명·카테고리·가격·시그니처·정렬·삭제의 읽기/탭 순서를
  보존한다.
- 사진 스트립은 내부 스크롤과 snap을 사용하고 삭제·순서 버튼의 터치 영역을 키운다.
- 오류 요약의 링크 이동 후 대상 필드가 sticky header/action에 가리지 않도록 scroll margin을 둔다.
- 완료 기준: 360px mobile과 768px tablet에서 신규 작성, 검증 실패, 재시도, 수정 저장을 완료하며
  실시간 추정치와 저장 동작에 접근할 수 있다.

### 5단계 — 상세·관찰·사진·비교

- 상세 제목/액션, 매출 highlight, 지표와 fact grid를 1/2/4열로 유동 배치하고 큰 금액과 긴 텍스트를
  줄바꿈한다.
- 관찰 폼·차트·목록은 mobile에서 세로 배치하되 수정/삭제 버튼과 날짜·점유율의 관계를 유지한다.
- 갤러리는 mobile 2열, tablet 3열, desktop 4열로 유지하고 lightbox에 safe-area 여백, 초점 이동/복귀,
  배경 스크롤 잠금을 적용한다.
- 비교표는 의도된 내부 가로 스크롤을 유지하고 첫 열과 header를 sticky 처리한다. 스크롤 안내와 끝단
  gradient를 제공하며 키보드 스크롤도 보존한다.
- 완료 기준: 빈 데이터·추정 불가·2개/3개 비교·긴 값에서도 정보나 조작이 잘리지 않는다.

### 6단계 — 자동 회귀 검사와 실기기 QA

- `responsive.spec.ts`를 추가해 360×800, 412×915, 768×1024, 1024×768, 1440×900에서 핵심 화면을
  검사한다. 전체 CRUD를 모든 폭에서 중복 실행하지 않고 폭별 layout smoke와 대표 성공/실패 흐름을
  분리한다.
- 모든 화면에서 문서 `scrollWidth <= clientWidth`를 검사하고 비교표·사진 스트립만 예외 컨테이너로
  명시한다.
- 고정 요소가 주요 버튼/필드와 겹치지 않는지, 핵심 터치 target이 44px 이상인지, 오류 필드가 화면에
  들어오는지 geometry assertion을 추가한다.
- 기존 axe 검사를 유지하고 키보드 탐색, 200% 확대, reduced motion, 화면 회전, iOS Safari와 Android
  Chrome 실기기를 수동 확인한다.
- 성공 경로: 로그인 → 목록 → 선택/비교, 신규 입력 → 저장 → 상세 → 수정.
- 실패 경로: 필수값 오류, 사진 부분 업로드 실패, 세션 만료, 잘못된 비교 URL, 빈/추정 불가 화면.
- 완료 기준: `npm run format:check`, `typecheck`, `lint`, `test`, `build`, `test:e2e`가 모두 통과하고
  기준 폭 before/after 캡처가 PR에 첨부된다.

## 6. 최종 완료 기준

- 320~1,440px에서 의도하지 않은 페이지 가로 스크롤이 없다.
- mobile/tablet의 모든 핵심 흐름에서 고정 메뉴·저장 bar·키보드가 콘텐츠와 조작을 가리지 않는다.
